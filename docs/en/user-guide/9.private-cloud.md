# Private Cloud Setup

Private Cloud lets your team run Agentrix tasks on servers or VMs that you control. Team members create tasks in the Agentrix web app, and Agentrix dispatches those tasks to your runner pool. Repositories, system dependencies, and local credentials stay in your environment.

## When to use it

- Your team wants a stable pool of Linux runners instead of relying on each developer's laptop.
- Your repositories, internal dependencies, build tools, or model gateway are only reachable from your company network.
- You want team members to submit tasks without giving everyone the runner secret.
- You need multiple machines under one private cloud, capped by your subscription's machine limit.

For single-user local execution, start with [CLI Setup](3.cli-setup.md) or [Desktop App Setup](2.desktop-setup.md).

## Prerequisites

- An Agentrix account with Private Cloud enabled.
- A Linux server or VM that can run continuously.
- Outbound access from the server to the Agentrix backend API. The hosted service defaults to `https://agentrix.xmz.ai`; replace it with your API URL for self-hosted deployments.
- Node.js 18+, npm, git, and the agent CLIs required by your tasks, such as Claude Code or Codex.
- A dedicated system user for the runner, for example `agentrix`.

See [Dependencies](4.dependencies.md) for install and check commands. Run `agentrix doctor` before starting the runner.

## Create a Private Cloud

1. Open the Agentrix web app.
2. Go to `Settings` -> `Private Clouds`.
3. Use the top-right menu to create a Private Cloud.
4. Open the detail page and copy the runner secret.

The runner secret registers runner machines for this cloud. It is not an invite link. Do not send it to regular members or commit it to a repository.

If the create action is unavailable, your current subscription may not include Private Cloud, or you may have reached the cloud limit.

## Start a runner on the server

Install the Agentrix CLI and the required agent:

```bash
npm install -g @agentrix/cli
npm install -g @anthropic-ai/claude-code
```

Install Codex CLI too if this runner will execute Codex tasks:

```bash
npm install -g @codex-ai/codex-cli
```

Start the daemon with the runner secret:

```bash
export AGENTRIX_SERVER_URL=https://agentrix.xmz.ai
export AGENTRIX_WEBAPP_URL=https://agentrix.xmz.ai
export AGENTRIX_HOME_DIR=/opt/agentrix
export CLOUD_AUTH_TOKEN=<runner-secret>

agentrix start
agentrix status
```

For self-hosted deployments, replace `AGENTRIX_SERVER_URL` and `AGENTRIX_WEBAPP_URL` with your own URLs. When `CLOUD_AUTH_TOKEN` is set, the CLI skips browser sign-in and registers the machine as a cloud runner with that secret.

## Start a runner with Docker

Use the CLI Docker image when you do not want to install Node.js, Claude Code, Codex, and sandbox dependencies on the host. The image runs `agentrix daemon` by default and requires `CLOUD_AUTH_TOKEN`, the runner secret from the Private Cloud detail page.

```bash
docker run -d \
  --name agentrix-runner \
  --restart unless-stopped \
  -e AGENTRIX_SERVER_URL=https://agentrix.xmz.ai \
  -e AGENTRIX_WEBAPP_URL=https://agentrix.xmz.ai \
  -e CLOUD_AUTH_TOKEN=<runner-secret> \
  -e AGENTRIX_BASE_URL=https://api.xmz.ai \
  -e AGENTRIX_API_KEY=<llm-gateway-api-key> \
  -e GITLAB_BASE_URL=https://gitlab.example.com \
  -e GITLAB_TOKEN=<gitlab-token> \
  -v agentrix-home:/home/agentrix/.agentrix \
  -v agentrix-workspaces:/home/agentrix/.agentrix/workspaces \
  ghcr.io/xmz-ai/agentrix/agentrix-cli:latest
```

For self-hosted deployments, replace `AGENTRIX_SERVER_URL` and `AGENTRIX_WEBAPP_URL` with your own Agentrix URLs and, if needed, use the `agentrix-cli` image from your registry. In this Docker flow, `AGENTRIX_API_KEY` is the LLM gateway key. Runner registration and task auth still use `CLOUD_AUTH_TOKEN`.

Before the container starts `agentrix daemon` or `agentrix start`, the entrypoint runs `agentrix llm-config apply` and generates Claude, Codex, and Gemini config from the environment:

| Config | Default path |
|---|---|
| Claude Code | `/home/agentrix/.claude/settings.json` |
| Codex | `/home/agentrix/.codex/config.toml` |
| Gemini | `$AGENTRIX_GEMINI_HOME/settings.json`, defaulting to `$AGENTRIX_HOME_DIR/config/gemini/settings.json` |

Auto-config writes missing files by default and leaves existing config alone. When `AGENTRIX_API_KEY` is missing and `AGENTRIX_API_KEY_FILE` is absent or unreadable, the entrypoint fails before daemon startup with a clear error. Set `AGENTRIX_LLM_CONFIG_FORCE=true` to rebuild the generated files. Set `AGENTRIX_LLM_AUTO_CONFIG=false` when you mount and manage all agent config yourself.

If the container needs access to a private GitLab instance, pass `GITLAB_BASE_URL` and `GITLAB_TOKEN` as well. After the daemon finishes cloud runner binding and connects to the API, it saves the token to the local encrypted store, syncs the user's API-side GitServer credential, and registers the current runner as a Git proxy node by default. Multiple runners can share the same GitLab config; API Git operations pick one online proxy node.

Common variables:

| Variable | Default | Description |
|---|---|---|
| `AGENTRIX_API_KEY` | — | LLM gateway key used to generate Claude, Codex, and Gemini config |
| `AGENTRIX_API_KEY_FILE` | — | Read the LLM gateway key from a file, useful with Docker secrets |
| `AGENTRIX_BASE_URL` | `https://api.xmz.ai` | LLM gateway URL; Codex automatically uses `/v1` under this URL |
| `AGENTRIX_CODEX_MODEL` | `gpt-5.5` | Default Codex model |
| `AGENTRIX_CLAUDE_MODEL` | `claude-sonnet-4-6` | Default Claude model |
| `AGENTRIX_CLAUDE_FAST_MODEL` | `claude-haiku-4-5` | Claude fast model |
| `AGENTRIX_CLAUDE_SUBAGENT_MODEL` | Same as `AGENTRIX_CLAUDE_MODEL` | Claude subagent model |
| `AGENTRIX_GEMINI_IMAGE_MODEL` | `gemini-2.5-flash-image` | Gemini image model |
| `AGENTRIX_CLAUDE_HOME` | `/home/agentrix/.claude` | Claude Code config directory |
| `AGENTRIX_CODEX_HOME` | `/home/agentrix/.codex` | Codex config directory |
| `AGENTRIX_CLAUDE_PATH` | `/usr/local/bin/claude` | Claude Code binary path |
| `AGENTRIX_CODEX_PATH` | `/usr/local/bin/codex` | Codex binary path |
| `AGENTRIX_GEMINI_HOME` | `$AGENTRIX_HOME_DIR/config/gemini` | Gemini config directory |
| `CLOUD_AUTH_TOKEN_FILE` | — | Read the runner secret from a file, useful with Docker secrets |
| `GITLAB_BASE_URL` | — | GitLab site URL for auto-configuration |
| `GITLAB_API_URL` | `<base-url>/api/v4` | GitLab API URL used by auto-configuration |
| `GITLAB_TOKEN` | — | GitLab token saved to the local encrypted store and synced as an API-side credential |
| `GITLAB_TOKEN_FILE` | — | Read the GitLab token from a file, useful with Docker secrets |
| `AGENTRIX_GITLAB_USE_AS_PROXY` | `true` | Whether to register the current runner as a Git proxy node |
| `AGENTRIX_GITLAB_AUTO_CONFIG` | `true` | Set to `false` to disable GitLab auto-configuration |

The image also checks the global Git identity on startup and fills in `Agentrix <agentrix@xmz.ai>` when it is missing. Set `AGENTRIX_GIT_USER_NAME` and `AGENTRIX_GIT_USER_EMAIL` to use a team identity.

## Run it with systemd

Use systemd or another process manager in production. First, confirm the installed `agentrix` path:

```bash
command -v agentrix
```

If you have not created the dedicated system user yet, create one:

```bash
sudo useradd --system --create-home --home-dir /opt/agentrix --shell /usr/sbin/nologin agentrix
```

Create an environment file:

```bash
sudo mkdir -p /etc/agentrix
sudo install -m 600 /dev/null /etc/agentrix/private-cloud.env
sudoedit /etc/agentrix/private-cloud.env
```

Add:

```ini
AGENTRIX_SERVER_URL=https://agentrix.xmz.ai
AGENTRIX_WEBAPP_URL=https://agentrix.xmz.ai
AGENTRIX_HOME_DIR=/opt/agentrix
CLOUD_AUTH_TOKEN=<runner-secret>
```

Create `/etc/systemd/system/agentrix-private-cloud.service`:

```ini
[Unit]
Description=Agentrix Private Cloud Runner
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=agentrix
WorkingDirectory=/opt/agentrix
EnvironmentFile=/etc/agentrix/private-cloud.env
ExecStart=/usr/local/bin/agentrix daemon
ExecStop=/usr/local/bin/agentrix stop
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Replace the `ExecStart` and `ExecStop` paths with the output from `command -v agentrix`. Use `agentrix daemon` under systemd because `agentrix start` launches a background daemon and exits. Then start the service:

```bash
sudo mkdir -p /opt/agentrix
sudo chown -R agentrix:agentrix /opt/agentrix
sudo systemctl daemon-reload
sudo systemctl enable --now agentrix-private-cloud
sudo systemctl status agentrix-private-cloud
```

View logs:

```bash
journalctl -u agentrix-private-cloud -f
tail -f /opt/agentrix/logs/daemon.log
```

## Verify the runner

Return to `Settings` -> `Private Clouds`, open the cloud detail page, and check that the runner count shows an online machine, such as `1/3`. You can also run these commands on the server:

```bash
sudo systemctl status agentrix-private-cloud
agentrix status
agentrix doctor
```

If systemd runs the daemon as the `agentrix` user, use the same `AGENTRIX_HOME_DIR` environment when checking from the command line.

If the server looks healthy but the web app has not updated, wait a few seconds and refresh. Runners report presence over WebSocket, so short delays can happen during network changes or daemon restarts.

## Invite teammates

The Private Cloud owner can create invite links from the cloud detail page. A teammate opens the link, signs in, and joins the private cloud under their own account.

Invite links add members. They do not start runners. Members can select the private cloud when creating tasks, but they cannot see the runner secret.

## Use it in tasks

When creating a task, select the private cloud in the runner or execution environment picker. When submitting work with `agentrix-run`, pass the matching `cloud-*` runner ID:

```bash
agentrix-run \
  --prompt "Run the test suite and fix failures" \
  --runner-id cloud-xxx
```

See [agentrix-run](8.agentrix-run.md) for CI usage.

## Security notes

- If the runner secret leaks, stop the old runners and recreate the private cloud or contact an administrator.
- Run the daemon with a dedicated low-privilege system user.
- Restrict permissions on `AGENTRIX_HOME_DIR`, the environment file, and log directories.
- Do not store the runner secret in repositories, plaintext CI variables, or shared shell profiles.
- Runner servers usually need outbound access to the Agentrix API. They do not need a public inbound port.

## Troubleshooting

### Runner does not come online

Check that `CLOUD_AUTH_TOKEN` is present in the daemon process environment. With systemd, inspect the `EnvironmentFile`. Then confirm `AGENTRIX_SERVER_URL` points to the correct API and review `daemon.log`.

### Startup opens browser sign-in

The daemon did not receive `CLOUD_AUTH_TOKEN`. Export it again, or restart the systemd service and check the environment file permissions.

### Tasks stay queued

Confirm that the private cloud detail page shows an online runner. Then run `agentrix doctor` on the runner and check git, Claude Code, Codex, and sandbox dependencies. Task logs are written to `$AGENTRIX_HOME_DIR/logs/worker-<taskId>.log`.

### Token is invalid or cloud is missing

This usually means the wrong secret was copied, or the runner connected to the wrong Agentrix API. Copy the runner secret again from the detail page and confirm `AGENTRIX_SERVER_URL` uses the same deployment.
