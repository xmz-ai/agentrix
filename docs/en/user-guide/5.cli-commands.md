# CLI Command Reference

## Global Options

| Flag | Description |
|---|---|
| `--version`, `-v` | Print the CLI version |
| `--help`, `-h` | Show help for any command |
| `--debug`, `-d` | Use local-debug mode (plaintext output, for debugging) |

---

## agentrix start

Start the daemon if it is not already running, then show its status.

```bash
agentrix start
```

**What it does:**

1. Authenticates (browser OAuth on first run, or validates existing credentials).
2. Checks critical dependencies (git, sandbox tools). Exits if any are missing.
3. Spawns the daemon as a detached background process.
4. Waits up to 5 seconds for the daemon to report ready.
5. Starts the upgrade-daemon if auto-upgrade is enabled.
6. Prints daemon status.

**Example:**

```
Starting Agentrix background service...
✓ Daemon started successfully

🤖 Daemon Status
✓ Daemon is running
  PID: 12345
  Started: 4/22/2026, 10:00:00 AM
  CLI Version: 1.2.3
  HTTP Port: 51234
```

**Related env vars:**

| Variable | Effect |
|---|---|
| `AGENTRIX_DISABLE_AUTO_UPGRADE=true` | Skip auto-upgrade check |

## agentrix doctor

Full system diagnostics — version, configuration, environment variables, authentication,
dependencies, and daemon status.

```bash
agentrix doctor
```

Use this as the first step when troubleshooting. It shows:

- CLI version, platform, Node.js version
- Daemon spawn paths (wrapper script, entrypoint)
- Configuration (home dir, server URL, log dir)
- Environment variables that affect Agentrix behavior
- Authentication status
- Dependency status (git, claude, codex, sandbox tools)
- Daemon status (running / stale / not running)

## agentrix llm-config apply

Generate Claude Code, Codex, and Gemini config from Agentrix environment variables. The CLI Docker image runs this command automatically before `agentrix daemon` or `agentrix start`; local and systemd deployments can run it manually.

```bash
export AGENTRIX_BASE_URL=https://api.xmz.ai
export AGENTRIX_API_KEY=<llm-gateway-api-key>

agentrix llm-config apply --verbose
```

For this command, `AGENTRIX_API_KEY` and `AGENTRIX_BASE_URL` point to the LLM gateway. `agentrix-run` also reads variables with those names, but there they mean Agentrix API options; see [agentrix-run](8.agentrix-run.md).

By default, the command writes only missing config files and leaves existing files alone. Codex config stays minimal; worker launch options control runtime sandboxing and approval policy.

**Options:**

| Option | Description |
|---|---|
| `--source env` | Read config from environment variables. Only `env` is supported |
| `--force` | Overwrite existing Claude, Codex, and Gemini config files |
| `--dry-run` | Show planned file writes without changing disk state |
| `--verbose` | Print each config file action |

**Related env vars:**

| Variable | Default | Description |
|---|---|---|
| `AGENTRIX_API_KEY` | — | LLM gateway key |
| `AGENTRIX_API_KEY_FILE` | — | Read the LLM gateway key from a file |
| `AGENTRIX_BASE_URL` | `https://api.xmz.ai` | LLM gateway URL; Codex uses `/v1` under this URL |
| `AGENTRIX_CLAUDE_HOME` | `$AGENTRIX_HOME_DIR/config/claude` | Claude Code config directory |
| `AGENTRIX_CODEX_HOME` | `$AGENTRIX_HOME_DIR/config/codex` | Codex config directory |
| `AGENTRIX_GEMINI_HOME` | `$AGENTRIX_HOME_DIR/config/gemini` | Gemini config directory |
| `AGENTRIX_CODEX_MODEL` | `gpt-5.5` | Default Codex model |
| `AGENTRIX_CLAUDE_MODEL` | `claude-sonnet-4-6` | Default Claude model |
| `AGENTRIX_CLAUDE_FAST_MODEL` | `claude-haiku-4-5` | Claude fast model |
| `AGENTRIX_CLAUDE_SUBAGENT_MODEL` | Same as `AGENTRIX_CLAUDE_MODEL` | Claude subagent model |
| `AGENTRIX_GEMINI_IMAGE_MODEL` | `gemini-2.5-flash-image` | Gemini image model |

## agentrix upgrade

Upgrade the CLI to the latest version on npm.

```bash
agentrix upgrade
```

This runs `npm install -g @agentrix/cli@latest` and:

- Also checks for agent updates (companion, etc.).
- Restarts the daemon automatically if it was running.

The CLI also upgrades itself automatically on each `agentrix start` (unless
`AGENTRIX_DISABLE_AUTO_UPGRADE=true`).

## agentrix logout

Unbind this machine from your Agentrix account.

```bash
agentrix logout
```

Removes `~/.agentrix/credentials.json`. The next `agentrix start` will open the browser
authentication flow again.

## agentrix ls

List sessions currently tracked by the running daemon.

```bash
agentrix ls
```

Each session corresponds to a running or recently-started worker process.

**Example:**

```
Active sessions:
[
  {
    "taskId": "task-abc123",
    "pid": 54321,
    "startedBy": "cli"
  }
]
```

Returns `No active sessions` if no workers are running.

## agentrix kill \<sessionId\>

```bash

```

## agentrix killall

Terminate all runaway agentrix processes found on the system.

```bash
agentrix killall
```

Use this when sessions are stuck or the daemon state is inconsistent. Reports how many processes
were killed.

## agentrix git-server add

Add a private GitLab server to the local daemon config and store the PAT used to access it.

```bash
agentrix git-server add \
  --base-url https://gitlab.example.com
```

**Options:**

| Option | Description |
|---|---|
| `--base-url <url>` | GitLab site URL, for example `https://gitlab.example.com` |
| `--api-url <url>` | GitLab API URL. Defaults to `<base-url>/api/v4` |
| `--pat-file <file>` | Read the PAT from a file; use `-` to read from stdin |

When `--pat-file` is omitted, the command prompts for the PAT interactively without echoing it.

```bash
printf '%s' "$GITLAB_PAT" | agentrix git-server add \
  --base-url https://gitlab.example.com \
  --pat-file -
```

The command prints JSON with `webhookUrl` and `webhookSecret`. The PAT and webhook secret are
encrypted under `~/.agentrix/credentials/`; `baseUrl` and `apiUrl` are stored as local config.

> This command requires a bound machine. If it reports that the Agentrix auth secret is missing,
> run `agentrix start` first.

## agentrix git-server list

List private GitLab config stored on this machine.

```bash
agentrix git-server list
```

The output includes the full local view: Git server ID, `baseUrl`, `apiUrl`, webhook endpoint,
current daemon `webhookUrl`, whether a PAT is configured, PAT user metadata, `webhookSecret`,
and cached project-level pipeline trigger tokens.

```json
[
  {
    "id": "corp-gitlab",
    "type": "gitlab",
    "baseUrl": "https://gitlab.example.com",
    "apiUrl": "https://gitlab.example.com/api/v4",
    "webhookEndpointPath": "/webhooks/gitlab/corp-gitlab",
    "webhookUrl": "http://192.168.1.10:30624/webhooks/gitlab/corp-gitlab",
    "patConfigured": true,
    "patMeta": {
      "username": "alice",
      "email": "alice@example.com",
      "lastValidatedAt": "2026-04-27T05:00:00.000Z",
      "expiresAt": null
    },
    "webhookSecret": "...",
    "projectTriggerTokens": {}
  }
]
```

If the daemon is not running, `webhookUrl` may be empty; run `agentrix start` and list again.

## GitLab Webhook Setup

The daemon's built-in web server can receive GitLab webhooks directly and convert supported
events into GitLab pipeline triggers.

Basic setup:

1. Run `agentrix start` to make sure the daemon is running.
2. Run `agentrix git-server add` to save the GitLab `baseUrl`, `apiUrl`, and PAT.
3. Run `agentrix git-server list`, then copy `webhookUrl` and `webhookSecret`.
4. In the GitLab project's Webhooks page, paste `webhookUrl` into URL and `webhookSecret` into Secret token, and select at least Issue events. To sync inbox reminders too, also select Merge request events and Comments.
5. If GitLab is not on the same machine, enable `daemonControl.allowLanAccess` in
   `~/.agentrix/settings.json` and restart the daemon.

```json
{
  "daemonControl": {
    "allowLanAccess": true
  }
}
```

### Supported Events and Mapping

The daemon webhook endpoint first validates GitLab's `X-Gitlab-Token`, then reports the payload
to the Agentrix repository inbox side channel. Separately, only events that support automatic
execution trigger a GitLab pipeline.

Pipeline triggers currently support these GitLab webhooks:

| GitLab webhook | Pipeline result | Normalized event |
|---|---|---|
| `event_type: "issue"` or `object_kind: "issue"` | Triggers a project pipeline | `AGENTRIX_EVENT_NAME=issue`, `AGENTRIX_EVENT_ACTION=<normalized_action>` |
| `merge_request` | Triggers a project pipeline | `AGENTRIX_EVENT_NAME=merge_request`, `AGENTRIX_EVENT_ACTION=<normalized_action>` |
| `note` with `@agentrix` or `/agentrix` in the comment body | Triggers a project pipeline | `AGENTRIX_EVENT_NAME=note`, `AGENTRIX_EVENT_ACTION=created/updated/deleted/...` |
| `pipeline` with status `failed` and `source` other than `trigger` | Triggers a project pipeline for failure diagnosis | `AGENTRIX_EVENT_NAME=pipeline`, `AGENTRIX_EVENT_ACTION=failed` |
| Ordinary `note`, non-failed `pipeline`, `source=trigger` failed pipeline, and other events | Does not trigger a pipeline; response body is `status: "ignored"` with a reason | Not applicable |

Issue actions are normalized before they are passed to the pipeline:

| GitLab action/state | `AGENTRIX_EVENT_ACTION` |
|---|---|
| `open`, `opened`, or `state: "opened"` | `opened` |
| `reopen`, `reopened` | `reopened` |
| `close`, `closed`, or `state: "closed"` | `closed` |
| `update`, `updated`, `edit`, `edited` | `edited` |
| Other non-empty action | Original value |
| No action and no inferable state | `unknown` |

Every daemon-triggered pipeline receives these base variables:

| Variable | Meaning |
|---|---|
| `AGENTRIX_EVENT_NAME` | Normalized event name: `issue`, `merge_request`, `note`, or `pipeline` |
| `AGENTRIX_EVENT_ACTION` | Normalized event action |
| `AGENTRIX_GIT_SERVER_ID` | Git server ID configured on this machine |
| `AGENTRIX_PROVIDER` | Always `gitlab` |
| `AGENTRIX_REPOSITORY_OWNER` | `project.path_with_namespace` without the final path segment; subgroups are preserved |
| `AGENTRIX_REPOSITORY_NAME` | Repository name |
| `AGENTRIX_TRIGGER_SOURCE` | Always `agentrix_daemon_webhook` |

Event-specific variables are added as follows:

| Event | Additional variables |
|---|---|
| `issue` | `AGENTRIX_ISSUE_NUMBER`, `AGENTRIX_ISSUE_TITLE`, `AGENTRIX_ISSUE_URL` |
| `merge_request` | `AGENTRIX_PR_NUMBER`, `AGENTRIX_HEAD_REF`, `AGENTRIX_BASE_REF`, `AGENTRIX_MR_TITLE`, `AGENTRIX_MR_URL` |
| `note` | `AGENTRIX_NOTEABLE_TYPE`, `AGENTRIX_NOTE_BODY`, `AGENTRIX_NOTE_ID`, `AGENTRIX_NOTE_URL`, plus either `AGENTRIX_ISSUE_NUMBER` or `AGENTRIX_PR_NUMBER` depending on the comment target |
| `pipeline` | `AGENTRIX_PIPELINE_STATUS`, `AGENTRIX_PIPELINE_SOURCE`, `AGENTRIX_PIPELINE_ID`, `AGENTRIX_PIPELINE_IID`, `AGENTRIX_PIPELINE_URL`, `AGENTRIX_REF`, `AGENTRIX_SHA`, and `AGENTRIX_PR_NUMBER` when an MR can be inferred |

Optional variables are present only when GitLab includes the matching payload field:

| Variable | Meaning |
|---|---|
| `AGENTRIX_ISSUE_TITLE` | Issue title; present when GitLab includes it in the payload |
| `AGENTRIX_ISSUE_URL` | Issue URL; uses the payload URL first, then falls back to project URL plus IID |

The repository inbox side channel consumes additional GitLab events, but it is separate from
pipeline triggering:

| GitLab webhook | Inbox normalization behavior |
|---|---|
| `note` | Non-system comments mark the issue/MR author and `@username` mentions as `needs_reply`; the comment author's own `needs_reply` is cleared; deleted mentions clear the matching status |
| `merge_request` | Reviewer changes maintain `needs_review`; draft MRs clear review reminders; closed or merged MRs resolve the MR inbox item; approve/unapprove clears or restores the reviewer's `needs_review` |
| `issue` | Assignee changes maintain `assigned`; closed issues resolve the issue inbox item |

Notes:

- The webhook URL is only the daemon endpoint. It does not contain the PAT, API URL, or pipeline trigger token.
- The webhook secret is matched against GitLab's `X-Gitlab-Token` request header.
- Pipeline trigger tokens are GitLab project-level tokens. The daemon creates or reuses an
  `Agentrix webhook bridge` trigger the first time it handles a webhook for a project, then
  encrypts the token locally.
- If GitLab rejects the pipeline trigger, for example because `.gitlab-ci.yml` is missing, the
  daemon logs the failure and returns HTTP `200` to GitLab with response body `status: "failed"`.
  This avoids GitLab retrying a business-level failure.

## Environment Variables

These variables modify CLI behavior without changing `settings.json`.

| Variable | Default | Description |
|---|---|---|
| `AGENTRIX_HOME_DIR` | `~/.agentrix` | Root state directory |
| `AGENTRIX_SERVER_URL` | `https://agentrix.xmz.ai` | Backend API URL |
| `AGENTRIX_WEBAPP_URL` | `https://agentrix.xmz.ai` | Web app URL (used for auth redirect) |
| `AGENTRIX_WORKSPACE_HOME_DIR` | `~/.agentrix/workspaces` | Task workspace root |
| `AGENTRIX_AGENTS_HOME_DIR` | `~/.agentrix/agents` | Custom agent install root |
| `AGENTRIX_CLAUDE_HOME` | `~/.agentrix/config/claude` | Claude Code config dir |
| `AGENTRIX_CODEX_HOME` | `~/.agentrix/config/codex` | Codex config dir |
| `AGENTRIX_GEMINI_HOME` | `~/.agentrix/config/gemini` | Gemini config dir |
| `AGENTRIX_API_KEY` | — | LLM gateway key read by `agentrix llm-config apply` and Docker auto-config |
| `AGENTRIX_API_KEY_FILE` | — | Read the LLM gateway key from a file |
| `AGENTRIX_BASE_URL` | `https://api.xmz.ai` | LLM gateway URL |
| `AGENTRIX_CLAUDE_PATH` | — | Override the `claude` binary path |
| `AGENTRIX_CODEX_PATH` | — | Override the `codex` binary path |
| `AGENTRIX_LLM_AUTO_CONFIG` | `true` | Whether the Docker image auto-generates LLM config before daemon/start |
| `AGENTRIX_LLM_CONFIG_FORCE` | `false` | Whether Docker auto-config overwrites existing LLM config |
| `AGENTRIX_DISABLE_AUTO_UPGRADE` | — | Set to `true` to disable automatic upgrades |
| `AGENTRIX_DISABLE_CAFFEINATE` | — | Set to `true` to allow the machine to sleep during tasks |
| `CLOUD_AUTH_TOKEN` | — | Cloud runner auth token; set to the runner secret when deploying a Private Cloud runner |
| `CLOUD_AUTH_TOKEN_FILE` | — | Read the cloud runner auth token from a file |
| `DEBUG` | — | Enable verbose debug logging |
