# CLI 命令参考

## 全局选项

| 标志 | 说明 |
|---|---|
| `--version`, `-v` | 打印 CLI 版本 |
| `--help`, `-h` | 显示任意命令的帮助信息 |
| `--debug`, `-d` | 启用本地调试模式（明文输出，用于排错） |

---

## agentrix start

启动守护进程（如未运行），然后显示其状态。

```bash
agentrix start
```

**执行步骤：**

1. 认证（首次运行时打开浏览器 OAuth，或验证已有凭据）。
2. 检查关键依赖（git、沙箱工具）。如有缺失则退出。
3. 将守护进程作为分离的后台进程启动。
4. 等待最多 5 秒，直到守护进程报告就绪。
5. 如果启用了自动升级，则启动 upgrade-daemon。
6. 打印守护进程状态。

**示例输出：**

```
Starting Agentrix background service...
✓ Daemon started successfully

🤖 Daemon Status
✓ Daemon is running
  PID: 12345
  Started: 4/22/2026, 10:00:00 AM
  CLI Version: 1.2.3
  HTTP Port: 51234
```

**相关环境变量：**

| 变量 | 作用 |
|---|---|
| `AGENTRIX_DISABLE_AUTO_UPGRADE=true` | 跳过自动升级检查 |

## agentrix stop

停止正在运行的守护进程。

```bash
agentrix stop
```

守护进程停止时，所有活跃的 Worker 会话都会被终止。

## agentrix doctor

完整的系统诊断——版本、配置、环境变量、认证、依赖项和守护进程状态。

```bash
agentrix doctor
```

排查问题时请以此命令为第一步。它会显示：

- CLI 版本、平台、Node.js 版本
- 守护进程启动路径（包装脚本、入口文件）
- 配置信息（主目录、服务器 URL、日志目录）
- 影响 Agentrix 行为的环境变量
- 认证状态
- 依赖状态（git、claude、codex、沙箱工具）
- 守护进程状态（运行中 / 状态陈旧 / 未运行）

## agentrix upgrade

升级 CLI 到 npm 上的最新版本。

```bash
agentrix upgrade
```

此命令执行 `npm install -g @agentrix/cli@latest`，并：

- 检查代理更新（companion 等）。
- 如果守护进程正在运行，自动重启。

每次 `agentrix start` 时 CLI 也会自动升级（除非设置了 `AGENTRIX_DISABLE_AUTO_UPGRADE=true`）。

---

## agentrix logout

解除此机器与 Agentrix 账户的绑定。

```bash
agentrix logout
```

删除 `~/.agentrix/credentials.json`。下次运行 `agentrix start` 时将重新打开浏览器认证流程。

## agentrix ls

列出当前守护进程跟踪的所有会话。

```bash
agentrix ls
```

每个会话对应一个正在运行或刚启动的 Worker 进程。

**示例输出：**

```
Active sessions:
[
  {
    "taskId": "task-abc123",
    "pid": 54321,
    "startedBy": "cli"
  }
]
```

如果没有 Worker 在运行，则返回 `No active sessions`。

## agentrix kill \<sessionId\>

通过任务 ID 停止特定的 Worker 会话。

```bash
agentrix kill task-abc123
```

## agentrix killall

终止系统上找到的所有失控的 agentrix 进程。

```bash
agentrix killall
```

当会话卡住或守护进程状态不一致时使用此命令。会报告已终止的进程数。

## agentrix git-server add

把一个私有 GitLab 服务写入本机 daemon 配置，并保存用于访问该 GitLab 的 PAT。

```bash
agentrix git-server add \
  --base-url https://gitlab.example.com
```

**选项：**

| 选项 | 说明 |
|---|---|
| `--base-url <url>` | GitLab 站点 URL，例如 `https://gitlab.example.com` |
| `--api-url <url>` | GitLab API URL。默认是 `<base-url>/api/v4` |
| `--pat-file <file>` | 从文件读取 PAT；使用 `-` 可从 stdin 读取 |

未指定 `--pat-file` 时，命令会交互式提示输入 PAT，并且不会回显。

```bash
printf '%s' "$GITLAB_PAT" | agentrix git-server add \
  --base-url https://gitlab.example.com \
  --pat-file -
```

命令会输出 JSON，包含 `webhookUrl` 和 `webhookSecret`。PAT 和 webhook secret 会加密保存在
`~/.agentrix/credentials/` 下；`baseUrl` / `apiUrl` 会以本机配置形式保存。

> 运行此命令前需要先完成机器绑定。若提示缺少 Agentrix auth secret，请先运行 `agentrix start`。

## agentrix git-server list

列出本机保存的私有 GitLab 配置。

```bash
agentrix git-server list
```

输出包含完整的本机信息：Git server ID、`baseUrl`、`apiUrl`、webhook endpoint、daemon 当前可用的
`webhookUrl`、PAT 是否已配置、PAT 用户元信息、`webhookSecret`，以及已缓存的项目级 pipeline trigger token。

```json
[
  {
    "id": "corp-gitlab",
    "type": "gitlab",
    "baseUrl": "https://gitlab.example.com",
    "apiUrl": "https://gitlab.example.com/api/v4",
    "webhookEndpointPath": "/webhooks/gitlab/corp-gitlab",
    "webhookUrl": "http://192.168.1.10:30624/webhooks/gitlab/corp-gitlab",
    "patConfigured": true,
    "patMeta": {
      "username": "alice",
      "email": "alice@example.com",
      "lastValidatedAt": "2026-04-27T05:00:00.000Z",
      "expiresAt": null
    },
    "webhookSecret": "...",
    "projectTriggerTokens": {}
  }
]
```

如果 daemon 没有运行，`webhookUrl` 可能为空；先运行 `agentrix start` 再查看。

## GitLab webhook 配置

daemon 自带的 web server 可以直接接收 GitLab webhook，并把符合条件的事件转成 GitLab pipeline trigger。

基本步骤：

1. 运行 `agentrix start`，确保 daemon 已启动。
2. 运行 `agentrix git-server add` 保存 GitLab `baseUrl`、`apiUrl` 和 PAT。
3. 运行 `agentrix git-server list`，复制 `webhookUrl` 和 `webhookSecret`。
4. 在 GitLab 项目的 Webhooks 页面中，将 `webhookUrl` 填到 URL，将 `webhookSecret` 填到 Secret token，并至少勾选 Issue events；如果还要同步 inbox 提醒，也勾选 Merge request events 和 Comments。
5. 如果 GitLab 不在本机，需要在 `~/.agentrix/settings.json` 中启用 `daemonControl.allowLanAccess` 并重启 daemon。

```json
{
  "daemonControl": {
    "allowLanAccess": true
  }
}
```

### 支持的事件与映射

daemon webhook endpoint 会先校验 GitLab 的 `X-Gitlab-Token`，然后把 payload 上报给 Agentrix 的仓库 inbox 通道；同时，只有支持自动执行的事件会触发 GitLab pipeline。

Pipeline trigger 当前支持这些 GitLab webhook：

| GitLab webhook | Pipeline 结果 | 规范化事件 |
|---|---|---|
| `event_type: "issue"` 或 `object_kind: "issue"` | 触发项目 pipeline | `AGENTRIX_EVENT_NAME=issue`，`AGENTRIX_EVENT_ACTION=<normalized_action>` |
| `merge_request` | 触发项目 pipeline | `AGENTRIX_EVENT_NAME=merge_request`，`AGENTRIX_EVENT_ACTION=<normalized_action>` |
| `note` 且评论中包含 `@agentrix` 或 `/agentrix` | 触发项目 pipeline | `AGENTRIX_EVENT_NAME=note`，`AGENTRIX_EVENT_ACTION=created/updated/deleted/...` |
| `pipeline` 且状态为 `failed`，并且 `source` 不是 `trigger` | 触发项目 pipeline，用于失败诊断 | `AGENTRIX_EVENT_NAME=pipeline`，`AGENTRIX_EVENT_ACTION=failed` |
| 普通 `note`、非失败 `pipeline`、`source=trigger` 的 failed pipeline 和其他事件 | 不触发 pipeline，响应体为 `status: "ignored"`，`reason` 会说明忽略原因 | 不适用 |

Issue action 会被规范化后传入 pipeline：

| GitLab action/state | `AGENTRIX_EVENT_ACTION` |
|---|---|
| `open`、`opened` 或 `state: "opened"` | `opened` |
| `reopen`、`reopened` | `reopened` |
| `close`、`closed` 或 `state: "closed"` | `closed` |
| `update`、`updated`、`edit`、`edited` | `edited` |
| 其他非空 action | 原值 |
| 没有 action 且无法从 state 推断 | `unknown` |

所有 daemon 触发的 pipeline 都会收到这些基础变量：

| 变量 | 含义 |
|---|---|
| `AGENTRIX_EVENT_NAME` | 规范化事件名：`issue`、`merge_request`、`note` 或 `pipeline` |
| `AGENTRIX_EVENT_ACTION` | 规范化后的事件动作 |
| `AGENTRIX_GIT_SERVER_ID` | 本机配置的 Git server ID |
| `AGENTRIX_PROVIDER` | 固定为 `gitlab` |
| `AGENTRIX_REPOSITORY_OWNER` | `project.path_with_namespace` 去掉最后一段后的路径，支持 subgroup |
| `AGENTRIX_REPOSITORY_NAME` | 仓库名 |
| `AGENTRIX_TRIGGER_SOURCE` | 固定为 `agentrix_daemon_webhook` |

不同事件会追加这些变量：

| 事件 | 追加变量 |
|---|---|
| `issue` | `AGENTRIX_ISSUE_NUMBER`、`AGENTRIX_ISSUE_TITLE`、`AGENTRIX_ISSUE_URL` |
| `merge_request` | `AGENTRIX_PR_NUMBER`、`AGENTRIX_HEAD_REF`、`AGENTRIX_BASE_REF`、`AGENTRIX_MR_TITLE`、`AGENTRIX_MR_URL` |
| `note` | `AGENTRIX_NOTEABLE_TYPE`、`AGENTRIX_NOTE_BODY`、`AGENTRIX_NOTE_ID`、`AGENTRIX_NOTE_URL`，并根据评论对象设置 `AGENTRIX_ISSUE_NUMBER` 或 `AGENTRIX_PR_NUMBER` |
| `pipeline` | `AGENTRIX_PIPELINE_STATUS`、`AGENTRIX_PIPELINE_SOURCE`、`AGENTRIX_PIPELINE_ID`、`AGENTRIX_PIPELINE_IID`、`AGENTRIX_PIPELINE_URL`、`AGENTRIX_REF`、`AGENTRIX_SHA`，能关联 MR 时还会设置 `AGENTRIX_PR_NUMBER` |

可选变量只有 GitLab payload 提供对应字段时才存在，例如：

| 变量 | 含义 |
|---|---|
| `AGENTRIX_ISSUE_TITLE` | Issue 标题；GitLab payload 提供时才存在 |
| `AGENTRIX_ISSUE_URL` | Issue URL；优先使用 payload 中的 URL，否则由项目 URL 和 IID 拼出 |

仓库 inbox 通道会额外消费部分 GitLab 事件，但它不等同于 pipeline trigger：

| GitLab webhook | Inbox 规范化行为 |
|---|---|
| `note` | 非 system comment 会把 issue/MR 作者和 `@username` 提及者标记为 `needs_reply`；评论作者自己的 `needs_reply` 会被清除；删除提及时会清除对应状态 |
| `merge_request` | reviewer 增删会维护 `needs_review`；draft MR 会清除 review 提醒；关闭或合并 MR 会 resolve 该 MR 的 inbox item；approve/unapprove 会清除或恢复对应 reviewer 的 `needs_review` |
| `issue` | assignee 增删会维护 `assigned`；关闭 issue 会 resolve 该 issue 的 inbox item |

说明：

- Webhook URL 只包含 daemon endpoint，不包含 PAT、API URL 或 pipeline trigger token。
- Webhook secret 对应 GitLab 的 `X-Gitlab-Token` 请求头，用于确认请求来自你配置的 GitLab webhook。
- Pipeline trigger token 是 GitLab 项目级 token。daemon 首次处理某个项目的 webhook 时会创建或复用
  `Agentrix webhook bridge` trigger，并把 token 加密缓存在本机。
- 如果 GitLab pipeline 触发失败（例如项目缺少 `.gitlab-ci.yml`），daemon 会记录日志，并对 GitLab 返回
  `200`，响应体中 `status` 为 `failed`，避免 GitLab 反复重试业务失败。

## 环境变量

这些变量可在不修改 `settings.json` 的情况下改变 CLI 行为。

| 变量 | 默认值 | 说明 |
|---|---|---|
| `AGENTRIX_HOME_DIR` | `~/.agentrix` | 根状态目录 |
| `AGENTRIX_SERVER_URL` | `https://agentrix.xmz.ai` | 后端 API URL |
| `AGENTRIX_WEBAPP_URL` | `https://agentrix.xmz.ai` | Web 应用 URL（用于认证跳转） |
| `AGENTRIX_WORKSPACE_HOME_DIR` | `~/.agentrix/workspaces` | 任务工作区根目录 |
| `AGENTRIX_AGENTS_HOME_DIR` | `~/.agentrix/agents` | 自定义代理安装根目录 |
| `AGENTRIX_CLAUDE_HOME` | `~/.agentrix/config/claude` | Claude Code 配置目录 |
| `AGENTRIX_CODEX_HOME` | `~/.agentrix/config/codex` | Codex 配置目录 |
| `AGENTRIX_DISABLE_AUTO_UPGRADE` | — | 设为 `true` 禁用自动升级 |
| `AGENTRIX_DISABLE_CAFFEINATE` | — | 设为 `true` 允许机器在任务执行期间进入睡眠 |
| `CLOUD_AUTH_TOKEN` | — | cloud runner 认证令牌；部署 Private Cloud runner 时设置为 runner secret |
| `DEBUG` | — | 启用详细调试日志 |
